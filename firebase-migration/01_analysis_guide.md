# Предварительный анализ структуры Firestore Rusty.Lub

**Статус: только статический анализ. Данные Firestore не читались и не экспортировались.**

Исходный проект: `psychic-origin-5kpr3`  
Новая целевая база: `rustylub`  
Database ID в обоих проектах: `ai-studio-rustylub-2e66bd8d-85dd-4eba-bb83-f354ddc97d59`

## 1. Важное ограничение достоверности

Список ниже собран по исходному коду и `firebase-blueprint.json`. Он **не подтверждает**, что каждая коллекция существует в текущей базе, и не показывает число документов, размер, вложенные коллекции или фактические типы полей. Фактическая инвентаризация требует чтения метаданных/документов и отдельного согласования затрат.

## 2. Коллекции, обнаруженные в проектных материалах

В исходном `firebase-blueprint.json` и коде встречаются следующие пути верхнего уровня:

- `chat_users` — профили чата, роли и статусы. В старой реализации может содержать устаревшие поля паролей; обращаться с ними как с особо чувствительными данными.
- `messages` — сообщения чата.
- `presence` — присутствие пользователей.
- `site_settings` — настройки сайта.
- `news` — публикации и новости.
- `payments` — сведения о платежах и статусах.
- `users` — профили пользователей.
- `tracked_players` — отслеживаемые игровые профили.
- `name_history` — история имён игроков.
- `sessions` — игровые сессии.
- `activity_logs`, `user_activities`, `security_logs` — журналы и пользовательская активность.
- `clan_posts`, `clan_comments`, `clan_tickets` — доска поиска команды и связанные записи.
- `clan_applications` — упоминается в ранних материалах; наличие и использование нужно подтвердить по коду/данным.

Этот перечень — отправная точка, а не готовый список экспорта. Также необходимо проверить подколлекции, документы с произвольными ID и коллекции, создаваемые динамически.

## 3. Почему команда индексов не подходит для оценки объёма

Команда `firebase firestore:indexes` не является инвентаризацией данных: индексы не сообщают число документов, размер базы или состав фактически существующих коллекций. Не использовать её как оценку стоимости или объёма миграции.

## 4. Безопасный порядок дальнейшего анализа

1. Проверить конфигурацию Firebase в репозитории и подтвердить, какие приложения/серверы обращаются к старому проекту.
2. Проверить разрешения учётной записи и текущие ограничения тарифа для обеих баз.
3. До любого чтения определить, какой минимальный запрос нужен, сколько операций он может создать и какие расходы возможны на старом проекте.
4. Сначала выполнить согласованный ограниченный read-only инвентарь; не выгружать содержимое документов на этом этапе.
5. Зафиксировать фактические коллекции, приблизительное количество документов, вложенные коллекции и используемые типы.
6. Только после оценки объёма и формата подготовить экспорт/импорт с сохранением типов Firestore, документных ID и ссылок.

## 5. Запреты до отдельного разрешения

- Не запускать экспорт, импорт, массовое чтение, запись или удаление.
- Не создавать Cloud Storage bucket и не использовать managed export/import.
- Не подключать биллинг к проекту `rustylub`.
- Не менять рабочую конфигурацию сайта с исходного проекта на новый.
- Не переносить открытые пароли. Учетные данные и хэши паролей требуют отдельного защищённого плана.

# Оценка расходов и ограничений миграции Firebase

**Статус: предварительная оценка рисков, не смета и не подтверждение бесплатности.**

## 1. Подтверждённые параметры проектов

| Параметр | Старый проект `psychic-origin-5kpr3` | Новый проект `rustylub` |
|---|---|---|
| Firestore edition | Enterprise | Standard |
| Регион | `europe-west2` | `europe-west2` |
| Free tier | Нет | Да |
| Billing enabled | Да | Нет |
| Database ID | Один и тот же пользовательский ID | Один и тот же пользовательский ID |

Эти сведения получены из ранее выполненного описания конфигурации баз. Они не показывают фактический размер данных и не означают, что старые операции уже создали расходы.

## 2. Что пока неизвестно

- Число документов и общий размер каждой базы.
- Количество и размер вложенных коллекций.
- Фактическое число пользователей Firebase Authentication.
- Размер Firebase Storage и состав объектов.
- Реальные суточные чтения/записи работающего сайта.
- Какие функции, API и внешние сервисы потребуются для переноса.
- Какие лимиты и условия бесплатного тарифа применимы к конкретной конфигурации Standard в регионе проекта на дату выполнения миграции.

Любые прежние оценки «10–50 МБ», «несколько тысяч документов» и утверждения о гарантированном попадании в бесплатные квоты **не подтверждены измерениями** и не должны использоваться для принятия решения.

## 3. Финансовые риски

- Чтение старой базы может тарифицироваться: старый проект работает с включённым биллингом и не имеет free tier.
- Новый проект сейчас без подключённого биллинга. Не подключать Blaze и не добавлять платёжный метод ради миграции.
- Нельзя обещать, что перенос гарантированно бесплатен: даже при бесплатном тарифе действуют ограничения квот, функций и связанных сервисов.
- Managed Firestore export/import через Cloud Storage не включать в план без отдельного анализа требований и стоимости.
- Не создавать bucket, Dataflow jobs и другие платные ресурсы для этой подготовки.

## 4. Безопасная процедура оценки

1. Не выполнять массовое чтение до согласования минимального read-only инвентаря.
2. Перед каждым запросом указать проект, базу, предполагаемое число операций и возможную тарификацию.
3. Сначала получить только необходимую агрегированную информацию; не скачивать пользовательские данные.
4. Отдельно оценить Auth, Firestore, Storage, Functions/Hosting и сетевые/внешние сервисы.
5. Сопоставить ожидаемые операции с актуальными официальными квотами Firebase/Google Cloud на дату миграции.
6. Остановиться, если для следующего этапа требуется подключить биллинг к `rustylub` или создать платный ресурс.

## 5. Текущий запрет на выполнение

До отдельного подтверждения владельца проекта запрещены экспорт, импорт, массовые чтения/записи/удаления и переключение рабочего сайта на новый Firebase. Старый проект сохраняется как резервный источник. Новый проект остаётся без биллинга.
